# Directions to beat AlignCoder: research decision report

**Date:** 2026-09-20  
**Scope:** repository-level code completion; target is to exceed AlignCoder under a controlled comparison.  
**Constraints:** no LiPO, no chosen/rejected pairs, no pairwise ranking loss, no policy-gradient/RL training.

## Executive decision

The best first direction is:

> **AST-Hybrid Target-Utility Knowledge Distillation**: keep AST-bounded evidence units, build a fixed hybrid candidate pool, use a frozen code generator offline to convert target-token likelihood into a soft distribution over candidates plus a null candidate, and train a UniXcoder student with one distributional KD loss.

This is the most direct way to retain AlignCoder's useful target alignment while removing its three main weaknesses: repeated online completion sampling, winner-take-all supervision, and weak base chunk boundaries.

This is a research hypothesis, not a guaranteed win. REPLUG already establishes the general idea of likelihood-supervised retrieval, so the contribution cannot be claimed as “KL distillation is new.” The credible contribution candidate is the controlled combination of completion-utility distribution KD, AST evidence units, hybrid repository coverage, and calibrated no-retrieval/context packing.

## 1. What the local reports establish

### AlignCoder's useful part

AlignCoder solves a real failure mode: the unfinished local query does not always contain the identifiers or intent needed to retrieve the right cross-file context. It improves retrieval through sampled candidate completions, dependency chunks, and target-PPL supervision. The local report records the strongest setting as `k=4` sampled candidates and substantial drops when query enhancement, dependency context, or retriever training is removed.

### AlignCoder's attack surface

The local implementation and report expose four weaknesses:

1. Multiple candidate completions require extra generator forwards at inference and can inject noisy tokens.
2. Only the lowest target-PPL candidate receives the positive signal. Other candidates are collapsed into “not winner,” even if several are useful.
3. Base chunks are formed from blank-line blocks; this can cut across functions, classes, and control structures. AlignCoder already uses tree-sitter for dependency chunks, so the precise target is the base evidence-unit construction, not “all of AlignCoder is non-AST.”
4. The reward is tied to one evaluator/generator proxy. Low target NLL is useful evidence, but it is not identical to exact match, compilation, execution, or human usefulness.

### What the other local reports add

- CAST supports AST split-then-merge units but does not solve target relevance.
- CodeRAG demonstrates practical offline teacher-to-student distillation, but its teacher reranks snippets rather than directly distilling final generator utility.
- GrepRAG shows that exact identifiers and structure-aware deduplication remain valuable even when dense retrieval is strong.
- DraCo shows that dataflow/type relations add information beyond text similarity.
- REVELA offers a non-pairwise self-supervised retriever pretraining route, but not direct evidence for repository completion.
- Repoformer, GRACE, and CODEFILTER show that retrieved context can be unnecessary or harmful; a good system needs a calibrated stop/filter policy.

## 2. External evidence that changes the design

The recent controlled chunking study is the most important adversarial result. It evaluates 864 combinations and reports that cross-file context length can dominate chunk strategy; Sliding Window and cAST are both on the cost-quality Pareto front, and Function chunking is never Pareto-optimal. Therefore the claim cannot be “AST always beats line chunks.” The correct claim is “AST gives better evidence boundaries, and its value must be tested inside a hybrid pool under matched context budgets.” See [How Does Chunking Affect Retrieval-Augmented Code Completion?](https://arxiv.org/abs/2605.04763).

ReCUBE adds a second warning: repository context utilization remains difficult even with strong models, and caller-centric exploration can help. It is useful as a stress test for whether the system uses repository structure rather than merely matching tokens. See [ReCUBE](https://arxiv.org/abs/2603.25770).

The direct target remains [AlignCoder](https://arxiv.org/abs/2601.19697). The proposed method must reproduce its generator, formatter, data split, and decoding before comparing improvements.

## 3. Recommended framework: AST-Hybrid Target-Utility KD

### 3.1 Model roles

**Student retriever:** `microsoft/unixcoder-base`, fine-tuned. It outputs one logit per candidate evidence unit and one null/no-retrieval logit.

**Offline task teacher:** a frozen code generator, initially `deepseek-ai/deepseek-coder-6.7b-base` as in the existing TCD-KD specification. It sees the visible local prefix plus one candidate at a time and scores only the true target tokens by teacher-forced NLL. It is never called at serving time.

**Final code generator:** a frozen generator with the same prompt and decoding protocol across all controlled runs. The primary engineering run may use the same DeepSeek-Coder-6.7B checkpoint; the reproduction track must also use the exact AlignCoder backbone being reproduced, such as its DeepSeek-Coder-1B/7B setting. This prevents a larger teacher from being mistaken for a retrieval improvement.

**Optional semantic teacher/miner:** `jinaai/jina-code-embeddings-1.5b`. Use it only for candidate coverage or an auxiliary ablation. Its cosine similarity is not the main label because semantic similarity does not guarantee completion utility.

### 3.2 Candidate construction

Build one fixed candidate pool per example without looking at the target:

1. AST-bounded source units from the user's AST chunker: function/class/block-aware split-then-merge, stable source spans, parent/scope metadata, and reconstructable text.
2. Exact import, symbol, signature, and dependency lookup.
3. Identifier-aware BM25/lexical retrieval.
4. Pretrained UniXcoder dense retrieval.
5. Optional Jina dense retrieval.
6. Optional dataflow/type lookup when the language/parser supports it.

Fuse the ranked lists with deterministic reciprocal-rank fusion and deduplicate by repository commit, file, span, and content hash. Keep the same pool for hard-label and soft-KD ablations. Start with 16 real candidates plus one null candidate; expand to 32 only after coverage and latency are measured.

The target file and target continuation must be excluded from candidate construction. AST parsing may be used to define the mask boundary, but all query features after masking must be reconstructed from visible code only.

### 3.3 Teacher label: what exactly is distilled

For candidate `c_i`, including `c_0 = empty`, compute:

```text
ell_i = mean target-token NLL from frozen generator G
g_i = ell_0 - ell_i
p_T(i) = softmax(g_i / tau_G)
```

The same visible local prefix and the same target-token mask must be used for every candidate. Otherwise a candidate that truncates more local context can appear better or worse for the wrong reason.

`p_T` is a soft usefulness distribution. It can represent several useful candidates, a weakly useful candidate, and the null option. This is the information AlignCoder's hard argmin label discards.

### 3.4 Student loss: the main loss is not RL

The student produces logits `z_S` over the fixed candidate IDs plus null:

```text
p_S = softmax(z_S)
L_main = KL(stopgrad(p_T) || p_S)
```

This is the complete main objective. There is no RL loss underneath it, no pairwise construction, and no LiPO. The frozen generator creates the offline target distribution; the student learns to reproduce it.

Optional objectives must stay separate in the experiment matrix:

- REVELA-style next-token/self-supervised pretraining is a Stage-0 initialization experiment, not a replacement for `L_main`.
- A pointwise keep/drop or harmful-context head is a D4 ablation.
- Jina similarity is an auxiliary semantic signal only if task-only KD has a coverage problem.

### 3.5 Serving path

```text
visible prefix
  → AST/lexical/dense/dataflow candidate union
  → UniXcoder student scores candidates + null
  → remove duplicate/overlapping spans
  → if candidate-vs-null margin is too small: no retrieval
  → otherwise pack top candidates under fixed cross-file budget
  → frozen code generator produces completion once
```

No teacher NLL, Jina teacher, draft completion, or pairwise reranking is used at serving time in the main system.

## 4. Directions worth trying, ranked

### Direction 1 — AST-Hybrid Target-Utility KD: **first priority**

This is the recommended main line described above. It has the best causal connection to AlignCoder's target-alignment gain, directly uses the user's AST work, and removes the need to manufacture chosen/rejected pairs.

**Keep if:** it beats the hard target-NLL baseline and AlignCoder on the prespecified primary slices with equal context and generator budget.

**Reject if:** it only improves NLL but not EM/ES, or its candidate coverage is lower than AlignCoder's.

### Direction 2 — AST-REVELA pretraining followed by target KD: **second priority**

Pretrain UniXcoder on repository-local NTP with cross-document attention over AST units, then fine-tune with the main distributional KD loss. This is fully non-pairwise and may improve cold-start retrieval.

**Why not first:** generic code co-occurrence can retrieve popular definitions instead of target-specific evidence, and the compute cost is larger. Run it only after D1 has a stable task-KD baseline.

### Direction 3 — One-pass information-need/query distillation: **latency branch**

Train a small query/need head offline from a teacher signal, then retrieve once from the hybrid index. This targets AlignCoder's repeated online completion sampling. It is attractive if D1 matches quality but not latency.

**Why not first:** an intermediate query can lose direct target utility and create a second teacher-student mismatch. It must be compared against D1 with the same candidate pool.

### Direction 4 — Utility-aware filtering and AST late expansion: **quality branch**

After D1 is stable, add deterministic parent/signature/caller expansion and a pointwise filter/null head. This targets harmful and fragmented context, not retrieval recall.

**Why not first:** it can improve results simply by giving the generator more tokens. Match the cross-file budget exactly and report the harmful-context rate.

## 5. Experiment ladder

### E0 — Controlled AlignCoder reproduction

Reproduce the native AlignCoder pipeline and record any gap from the paper. Lock repository splits, prompt formatter, target masking, generator checkpoint, decoding, and number of generator forwards.

### E1 — Evidence-unit and pool diagnostic

Compare line/blank-line, sliding-window, AST-only, and AST-hybrid pools without training. Measure candidate coverage, duplicate rate, cross-file token usage, and exact generator completion under teacher-ranked candidates.

### E2 — Supervision ablation

On the identical AST-hybrid pool compare:

1. pretrained UniXcoder;
2. hard target-NLL winner CE;
3. soft target-utility KD;
4. soft KD without null;
5. soft KD with null.

This is the key test of whether the proposed improvement comes from soft distributional supervision rather than just a better pool.

### E3 — Optional teachers and representation prior

Add Jina only as candidate miner, then only as auxiliary score. Separately run REVELA-style NTP pretraining. Never combine all additions in the first comparison.

### E4 — Filtering, expansion, and latency

Add overlap deduplication, null gating, AST parent/signature expansion, and one-pass need/query distillation one at a time. Report accuracy and latency together.

## 6. Metrics and acceptance criteria

Primary metrics: exact match on CrossCodeEval Python/Java/C#/TypeScript where available and RepoEval line/API. Secondary metrics: edit similarity, identifier metrics, candidate recall/coverage, harmful-context rate, null-gate rate, prompt tokens, retrieval latency, generator latency, and total generator forwards.

Use three seeds or bootstrap confidence intervals on fixed examples. Break down by explicit imports, implicit calls, nested scopes, long files, and duplicate-heavy repositories. Add ReCUBE or another usage-aware stress set when its protocol can be reproduced; do not replace the direct completion benchmarks with it.

The main direction is a success only if:

1. its candidate coverage is not lower than the controlled AlignCoder baseline;
2. soft KD beats hard target-NLL supervision on the same pool, or the report honestly drops the soft-KD claim;
3. EM/ES improves on the primary slices under equal generator/context budget;
4. serving removes AlignCoder's repeated draft sampling without an unacceptable quality loss;
5. the gain survives sliding-window, lexical-only, and no-retrieval comparators.

## 7. Main risks and how to handle them

### Target NLL is not exact match

Use target NLL for scalable offline supervision, but validate teacher-ranked candidates with a held-out generator and, where available, compile/test or usage-aware metrics. If NLL and EM disagree, calibrate temperature or reduce the teacher's role rather than hiding the mismatch.

### AST is not automatically better

Keep the sliding-window comparator and control the context length. Report whether AST improves coverage, harmful-context rate, or only boundary aesthetics.

### Jina may be semantically strong but task-weak

Separate Jina mining from Jina auxiliary KD. If adding Jina reduces exact identifiers or increases harmful retrieval, set its auxiliary weight to zero while retaining any coverage benefit.

### REPLUG limits novelty

The paper must position this work as a repository-code completion adaptation with AST/hybrid evidence, null calibration, and latency controls, then compare directly against a REPLUG-style code baseline.

## Final recommendation

Implement **Direction 1 only** as the first framework:

```text
AST-Hybrid fixed pool
→ frozen DeepSeek-Coder teacher target-NLL distribution
→ UniXcoder candidate+null soft KD
→ student-only serving
→ one frozen generator call
```

Keep Direction 2 as the next ablation if the student is under-initialized, Direction 3 if latency is the bottleneck, and Direction 4 if harmful/duplicate context is the bottleneck. Do not merge them into the main claim before each component wins its controlled ablation.
